## A06 Threat Model and Minimum Trusted Computing Base (2026-11-03)

This section summarizes boundaries based on the current implementation; it is not a security certification or adversarial audit. Threat sources include model/provider output that may be erroneous, prompt-injected, or forged; generated candidate source; imported project source; and reference packages. Reference content and model text are data, not control authorization. Tool schemas/policy and the runtime validate parameters, paths, baseline hashes, permitted tools, and change size; the in-process capability in scope/session/expiry/revocation (`application_policy.py`) does not isolate the host process or protect against a same-privilege process directly modifying memory or files.

The minimum trusted computing base (TCB) consists of: the operator's selection and authorization of model permissions, trusted adapter commands, container image/deployment root, and independent acceptance inputs; the controller, tool dispatch/policy, and its local filesystem; the configured provider and transport identity/protocol boundary; `application_builder.py`, trusted execution adapters, the local Docker/Podman daemon, host kernel, and exact image; and the independent business contract/oracle and its custodian. If any of these components is compromised, misconfigured, or shares an error, the current mechanisms cannot guarantee safety/correctness. Model-generated candidates, imported projects and reference material, provider-returned text/tool-call intent, and reports produced by candidate execution are untrusted. Although the builder/container, filesystem, and oracle can serve as acceptance authorities, they must also be trusted under the above TCB assumptions; a report itself is not independent external proof.

Observed implementation limitations: Candidate paths/file contents and candidate schemas are validated; staged files have a manifest and SHA-256 check. Existing project transactions additionally have import baselines, source-conflict detection, an atomic active pointer, and pointer rollback (`application_project.py`); the source tree is not rewritten by these commit/rollback APIs. The lock binds the exact toolchain image ID, package versions, source allowlist, and artifact SHA-256; the environment plan declares candidate execution as network-free, with candidate and cache mounted read-only (`application_dependencies.py`). Actual execution isolation still depends on the adapter, container daemon, host kernel, and image; a manifest declaration does not prove daemon behavior. The business contract is passed from the host to the trusted builder; application preflight excludes oracle answers that are byte-identical to reference files, but explicitly does not block answers that leak through rewriting/paraphrase (`application_build.py`).

Network and ownership: Provider access is an explicitly configured outbound path authorized by the operator; source code/task context may be sent to that provider. Current endpoint checks and transport restrictions such as no credentials/no redirects do not mean the provider is trusted or the content is confidential. Dependencies are fetched only over explicitly authorized HTTPS with an allowlist and expected digest; the build network plan is `none`. Neither candidate nor reference packages can independently grant new host-tool permissions. The controller owns the source baseline and commit pointer; the operator owns source/reference materials, provider and image selection, and acceptance oracle; the candidate owns only its isolated snapshot. Persistent session/candidate/control capability files must remain private and must not be given to the model; users may modify source files and thereby trigger a conflict rather than being silently overwritten.

Known capability gaps: The container/host daemon, provider, controller, dependency artifacts, and oracle were not independently verified in this work; a digest proves only the bytes read, not source authenticity (except where a signature/authorization is independently verified). The secret heuristic is not general-purpose DLP; the oracle-copy check does not detect semantic leakage; in-process capabilities do not constitute a cross-process security boundary; local host privileges, denial of service, container escape, supply-chain poisoning, and common-mode errors remain within the TCB or outside the covered scope. All conclusions are limited to the implementation read and specific tests; they do not support a claim of security certification or production-grade security.
